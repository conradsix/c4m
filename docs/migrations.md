# Migrations

The engine's schema is built by its own EF Core migrations in `src/ConradSix.C4M/Data/Migrations`, which hosts apply
with `MigrateC4MAsync`. A host's own migrations never touch the `cms` schema.

## Adding one

```bash
./migration.sh add -n AddPageSummary
```

The script restores the EF tools, uses the sample host as the startup project, writes the migration to
`Data/Migrations` and marks it `<auto-generated />`. Names are letters only. Adding a migration needs no database.

`./migration.sh update`, `rollback` and `remove` work on the repo's docker-compose database, or on the one in
`C4M_CONNECTION_STRING`.

## Rules

- **Every change ships to databases with content in them.** A migration that adds a required column gives it a value
  for existing rows, and a migration that drops or renames something says what hosts lose.
- **SQL functions and triggers** are files in `Data/Migrations/Sql`, embedded in the assembly and run with
  `migrationBuilder.ExecuteSqlResource("name.sql")`. Their bodies name the `cms` schema, so they don't depend on a
  connection's `search_path`.
- **Never edit a released migration.** Hosts have already run it; a fix is a new migration.
- **The identifiers in [fixed-identifiers.md](fixed-identifiers.md) stay as they are.**
- **Check the model and migrations agree** before committing:

  ```bash
  dotnet ef migrations has-pending-model-changes --project src/ConradSix.C4M --startup-project samples/ConradSix.C4M.SampleHost
  ```

The engine's tests run on a database built by the migrations alone, as a new host's is.
